# Each Operator Secret Is Stored for What It Is

The operator carries three secrets and each is stored differently. The
**password** is hashed slowly, with ASP.NET Core's `PasswordHasher<T>` —
PBKDF2-HMAC-SHA512 — and rehashed at the current cost whenever a sign-in
succeeds. A **backup code** is hashed once with SHA-256 and is never recoverable.
The **TOTP secret** is encrypted with the key on the host volume, exactly as a
token is
([ADR 0022](./0022-a-token-is-recoverable-and-encrypted-rather-than-hashed.md)).
Three storages for three secrets looks like an inconsistency and is the opposite
of one: what the product has to be able to *do* with each of them differs, and
that is what decides. It has to prove the password without holding it, prove a
backup code without holding it, and compute a TOTP code — which cannot be done
without the secret itself.

## Why the framework's hash and not Argon2id

Argon2id is the stronger answer and it was not taken. It is memory-hard, which is
the property that takes the advantage away from the hardware an offline attacker
would bring, and against a human-chosen password behind nothing but a minimum
length ([Signing in](../sign-in.md)) that advantage is the whole game. Against it:
there is no Argon2 anywhere in .NET 10, neither in the base class libraries nor
in the shared frameworks, so it is a third-party package on the sign-in path of a
product whose case is being small. `PasswordHasher<T>` arrives with the ASP.NET
Core shared framework at no dependency cost at all, is maintained by the people
who ship the runtime, and already carries a version marker in the hash it writes.

What made that trade affordable was the **second factor, which was mandatory and
could not be turned off** ([ADR 0016](./0016-the-second-factor-is-totp.md)): a
cracked password on its own opened nothing.
[ADR 0017](./0017-a-wrong-password-never-locks-the-account.md) rested the whole of
its argument on that same fact, and this decision rested on it a second time. The
sentence that followed here said both were reopened together if the second factor
ever became optional, and
[ADR 0041](./0041-the-second-factor-is-offered-not-required.md) made it optional.

**So this one was reopened**, and it is answered in
[ADR 0042](./0042-the-password-carries-more-so-it-gets-longer.md) rather than
here: on an installation whose operator enrolled no second factor, a stolen dump
ground offline yields the one credential that opens everything, and what changed
is not the algorithm but what the password is worth — so what moved was its
minimum length. The hasher below stands as chosen, and the premise it was chosen
under is gone.

## Consequences

**A stolen database dump can be ground offline, and that is the accepted cost.**
It is the one thing on this list an attacker gets real leverage on, `VISION.md`
expects dumps to exist on other machines, and PBKDF2 is a worse obstacle than
Argon2id would have been. It is stated rather than argued away.

**The parameters are versioned and a successful sign-in silently rehashes.** That
is what makes "raise the cost later" a path rather than an intention, and it is
the same path a move to Argon2id would take — the verifier learns to read one
more format, and the next sign-in writes the new one. A password that is never
signed in with keeps its old hash, which costs nothing, because it is also a
password nobody is signing in with.

**A backup code gets a fast hash and no salt, deliberately.** It is generated by
the installation at full entropy, so there is no candidate list to grind and
nothing a slow hash would buy; a salt defends against a precomputed table that
cannot exist for a value of this size. What it needs is a constant-time
comparison, which is not the same property and is not optional.

**A backup code is not recoverable, and a token is.** ADR 0022 stored a token so
that the operator can read it back, and this is the deliberate opposite. The
reasoning there turned on a token being a copy of something the operator can
already reach; a backup code is precisely what stands in when they cannot reach
anything, so there is no session that could be trusted to display one.
`docs/sign-in.md` shows a set once, and this is what makes that true rather than
a convention.

**A backup code is consumed by a timestamp, not by deletion.** "How many remain"
is then a filtered count, which is what `docs/sign-in.md` requires to be shown
whenever one is spent, and a code that has been used stays visibly used instead
of vanishing.

**A fresh set replaces the previous one wholesale, and re-enrolment overwrites.**
Generating backup codes deletes the previous rows and writes new ones;
re-enrolling the second factor overwrites the secret on the operator rather than
retiring it beside a new one. Nothing that has been replaced survives, which
is the property worth having in a product with one account and no audit reader.
The date of the last enrolment is kept as a date — that is the part of a history
that is worth something, and it does not require keeping the secret it belonged
to.

**Encrypting the TOTP secret puts the second factor behind the key on the
volume.** An installation restored without its key cannot verify a code at all,
and the backup codes — which are hashed and need no key — become the only way
in, with
[Host Recovery](./0013-host-recovery-returns-the-installation-to-unclaimed.md)
behind them. That is one more reason the key belongs in the backup and one more
thing [ADR 0024](./0024-a-backup-is-one-artifact-holding-both-halves.md) is
carrying, which it did not name.

**The hashing is a port, not a domain rule.** `PasswordHasher<T>` lives in the
ASP.NET Core shared framework, which `Logaffe.Domain` does not have and should
not acquire ([ADR 0030](./0030-the-solution-is-four-layers-not-one-project.md)).
The rules that are stated in the documents — the minimum length, the single use
of a backup code — belong in Domain; the algorithm that turns a password into
bytes is an adapter, and swapping it is the reason it is one.
